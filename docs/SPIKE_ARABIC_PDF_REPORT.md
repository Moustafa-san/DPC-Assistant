## 1. التحدي الهندسي في معالجة اللغة العربية في ملفات PDF

تختلف معالجة النصوص العربية في ملفات PDF جذرياً عن النصوص اللاتينية نظراً للخصائص البنيوية التالية:
1. **اتصال الحروف وتعدد أشكالها السياقية (Contextual Shaping):** الحرف العربي يمتلك حتى 4 أشكال طباعية (منفرد، أول، وسط، أخير) بناءً على موقعه وقواعد الاتصال.
2. **الاتجاهية الثنائية (Bi-Directional / Bidi):** كتابة النص من اليمين إلى اليسار (RTL) مع احتواء أرقام أو كلمات إنجليزية تسير من اليسار إلى اليمين (LTR).
3. **التشكيل وضبط الحركات (Diacritics & Combining Marks):** علامات التشكيل التي تعلو أو تسفل الحرف دون احتساب مسافة عرضية إضافية.
4. **تضمين الخطوط (Font Embedding):** ملفات PDF لا تدعم الخطوط العربية الافتراضية للأنظمة اللاتينية (Helvetica / Times) وتتطلب تضمين خط عربي أصيل بصيغة TTF/OTF مرخصة محلياً (مثل Cairo أو Alexandria أو Amiri).

## 2. المقارنة الهندسية بين الخيارات المتاحة

| معيار المقارنة | الخيار أ: `@react-pdf/renderer` مع Reshaper | الخيار ب: الطباعة الأصلية عبر المتصفح (`window.print()` / CSS Paged Media) | الخيار ج: توليد خادمي عبر Playwright / Chromium Headless | الخيار د: `jsPDF` + `html2canvas` (Bitmap Rasterization) |
|---|---|---|---|---|
| **صحة اتصال الحروف العربية** | يحتاج Reshaper يدوي (مثل خوارزمية Unicode Presentation Forms-B المنفذة في `src/lib/pdf/arabic-reshaper.ts`) | **مثالية 100%** عبر محرك تخطيط المتصفح الطبيعي | **مثالية 100%** عبر محرك Chromium | تظهر كنقاط بكسل مصفوفة وليست نصوصاً قابلة للتحديد |
| **دعم RTL وتداخل الأرقام والعملات** | يحتاج معالجة Bidi يدوية معكوسة لتجنب قلب الكلمات | **أصيل وتلقائي** عبر خاصيتي `dir="rtl"` و`dir="ltr"` في CSS | **أصيل وتلقائي** عبر محرك المتصفح | معقد ويتأثر بتوقيت الرسم على Canvas |
| **قابلية نسخ وتحديد النص في PDF** | نعم (نص متجهي Selectable Text) | **نعم (نص متجهي عالي النقاء)** | **نعم (نص متجهي عالي النقاء)** | **لا** (مجرد صورة نقطية ممسوحة) |
| **حجم حزمة الكود والتنزيل** | كبير نسبياً (~550KB في حزمة المتصفح) | **صفر كيلوبايت إضافي (Zero-bundle overhead)** | صفر في العميل (ينفذ خادمياً كـ Microservice أو API) | متوسط (~120KB) |
| **تقسيم الصفحات (Pagination & Breaks)** | يدعم مكونات `<Page>` يدوياً | **ممتاز** باستخدام قواعد CSS الحديثة: `break-inside: avoid` و`@page` | **ممتاز** مع دعم الرؤوس والتذييلات التلقائية | ضعيف جداً (يقطع النصوص عشوائياً بين الصفحات) |
| **الأداء والسرعة** | معالجة ثقيلة في الذاكرة عند كثرة البنود | **فوري ولحظي** | يحتاج وقت تشغيل عملية المتصفح (1-2 ثانية) | بطيء ويستهلك الذاكرة لرسم Canvas |

## 4. القرار المعماري المعتمد لملفات PDF (Architectural Decision for Gate 5)

بناءً على الأدلة والقياسات المستخلصة، يُعتمد النموذج الهجين التالي (Hybrid PDF Architecture):

1. **الطبقة الأساسية الأولى (Client-side Zero-dependency Export):**
   - اعتماد **قالب طباعة ويب مخصص (Dedicated CSS Paged Media View)** في شاشات الفواتير وعروض الأسعار.
   - تنسيق القالب باستخدام خطوط **Cairo** و**Alexandria** المضمنة، مع استخدام:
     ```css
     @media print {
       @page {
         size: A4 portrait;
         margin: 15mm;
       }
       .no-print { display: none; }
       .avoid-page-break { break-inside: avoid; }
     }
     ```
   - **المزايا:** يتيح للمصور توليد وحفظ وطباعة الفاتورة أو البريف بصيغة PDF عالية الجودة مباشرة من المتصفح أو تطبيق الهاتف بدون أي استهلاك للإنترنت، وبدون تحميل حزم جافاسكربت ثقيلة، وباتصال كامل للحروف العربية وتشكيلها الصحيح.
2. **الطبقة الخادمية الآلية (Automated Serverless PDF Rendering):**
   - للاحتياجات التي تتطلب تنزيلاً تلقائياً من روابط المشاركة العامة للعملاء (`/<locale>/p/<token>`)، يُستخدم معالج خادمي خفيف (Playwright/Chromium Headless API) يحول نفس القالب المنضبط إلى ملف PDF رسمي دون تعريض تفاصيل المصور الداخلية للخطر.
3. **استبعاد محركات Canvas النقطية:**
   - يُحظر استخدام `html2canvas` أو تقنيات تصوير الشاشة النقطية للفواتير لتعارضها مع معايير الجودة والطباعة المهنية.
